# prorab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 11–12 additionally follow superpowers:writing-skills (RED → GREEN → REFACTOR with pressure scenarios).

**Goal:** A Claude Code skill `prorab` that lets one session (the foreman) run Claude crews in herdr panes across sites for hours without the customer, with work orders in beads, acceptance by evidence, control of context, limits and the dollar budget, handovers and a morning report.

**Architecture:** A lean English `SKILL.md` holds the rules; all mechanics live in small stdlib-Python scripts under `prorab/scripts/` (one responsibility each) that wrap the `herdr` and `bd` CLIs and read Claude transcripts. All numbers (thresholds, budget, prices, context windows) live in one file, `prorab/references/defaults.json`. State lives in the foreman's office's own beads database (the journal).

**Tech Stack:** Python 3 standard library only (`unittest` for tests), POSIX sh for the status-line tap, herdr ≥ 0.9.5, bd ≥ 1.3 (embedded Dolt), Claude Code 2.1.x, superpowers plugin (recommended, with fallback).

**Spec:** `docs/superpowers/specs/2026-10-21-prorab-design.md` (approved 2026-10-21; English rewrite with amendments S, L, G, R, E). Its glossary gives one English term per concept and the code identifier that carries it; this plan uses those terms and identifiers everywhere. Read the spec before any task; this plan argues from it, and where they disagree the spec wins.

**Amendments** (customer-approved 2026-10-21; short tags in the text): **S** — crew scheduling, the night reserve and the command "ignore limits and finish"; **L** — stale limits from idle sessions; **G** — patterns adopted from Gas City (ideas only: nothing is copied from Gas City code or fixtures; pattern labels P1–P16); **R** — estimates, spend and the shift budget in US dollars at API prices, counts only as machine protection; **E** — everything in English, identifiers too. "Answer n" refers to the foreman's binding answers 1–5 of shift 2; R39–R52 to the foreman's rulings.

**Rulings from the implementation** (the foreman's, made while Tasks 8b–8c ran; folded into the tasks below):

- **R45** — the composer is the line starting with `❯` (U+276F) directly between two horizontal-rule lines of `─` (U+2500); an empty composer is the bare `❯`; `>` is accepted as a fallback for older versions under the same rule; a choice-dialog line such as `❯ 1. Yes` is never a composer (verified on a live Claude Code pane).
- **R46** — `send` waits `agent prompt --wait --until working --until done --until blocked` (herdr's `--wait` gate already requires an observed `working` or `blocked` from a non-working state); after `stalled`, the single recovery Enter is followed by a wait `--until working --until blocked` only, because a standalone `agent wait` matches the current state and the pane was already `idle` or `done`: `working` → accepted, `blocked` → blocked, anything else or a timeout → `unconfirmed`; a wait output with no recognisable status falls back to `agent get`.
- **R47** — a reset zone in a limit message is resolved with `zoneinfo` (`UTC`, `GMT`, `Region/City`); an unresolvable zone gives an unknown reset (`None`), never local time.
- **R48** — a failed restart must not eat the restart cap; with it two report-check fixes: an empty item under "Changed files" is a rejection, never a crash, and the report's SHA must lie in `<base>..HEAD`.
- **R49** — the crew restart point is a successful `agent start`: from then on the session record names the new session and the restart counts toward the per-work-order restart limit, whatever the delivery result; a failure before `agent start` changes nothing.
- **R50** — in the monitor, a final provider error replaces `settled` for that crew's episode, like consent prompts and limit screens.
- **R51** — `crew.state` takes the already-read screen as `screen=` (an empty text is a read screen), so the monitor never reads a screen twice.
- **R52** — `crew.py check_report` rejects a stage report whose heavy-run count cannot be verified from records (no `--stage`, or the stage has no start time) with `heavy runs not verifiable`; the foreman always runs `check_report --stage <stage>` before `accept`, and `accept` itself does not check.

## Global Constraints

- Required: herdr ≥ 0.9.5 with `HERDR_ENV=1`, bd ≥ 1.3. Nothing else is installed. prorab never initialises or edits the beads of a site.
- Python: standard library only; no pip, no uv, no third-party modules. Scripts start with `#!/usr/bin/env python3` and import siblings from `prorab/scripts/` (add `os.path.dirname(__file__)` to `sys.path`).
- Crews are Claude only (`--kind claude`). Codex is never started as a crew. There is no Russian-polish command: the key `polish_cmd` leaves `defaults.json` and the kv override `polish.cmd` is gone (R39, Task 8c.1).
- Journal: `BEADS_DIR=~/projects/prorab/.beads` for every `bd` call made by prorab. `.beads/` is in the repo `.gitignore`.
- No customer data in `prorab/`, `docs/` or the repo `CLAUDE.md`: no names of the customer's projects, no paths into them, no client data, no quotes from real sessions, no names of personal tools. Examples, fixtures and scenarios are synthetic and neutral only (e.g. `demo-app`, `/home/user/projects/demo-app`). Guarded by `prorab/tests/test_no_private_data.py`.
- Language (E): everything generated or shipped is English — `SKILL.md`, everything in `references/` (including the act and message templates sent to crews), the string values of `defaults.json`, every template the scripts render, work orders, stage acts, handover acts, customer gates, push notifications, the morning report, the monitor's event texts, strings and docstrings in scripts and tests (fixtures' expected texts included), the pressure scenarios, the trigger evals, the spec and this plan; commit messages too. Identifiers are English as well: module, function, variable and test names, CLI subcommands and flags, kv keys, bead labels, act kinds, event names, `defaults.json` keys, file and directory names take the glossary's terms, and no Russian word appears in them — neither in Cyrillic nor in Latin transliteration. Only the skill name `prorab` and names derived from it stay (`prorab:active`, `prorab:handoff`, `~/projects/prorab`, `~/.cache/prorab`, the branch `prorab/<id>`). Every trigger phrase in the `description` of `SKILL.md` appears in English and in Russian, plus `/prorab`; the trigger evals cover both languages, should-trigger and should-not-trigger alike. The foreman answers the customer in chat in whatever language the customer writes in; generated files stay English. The customer's Russian commands are described in English ("the customer's command 'ignore limits and finish', in any language"). Guards: no transliteration (Task 8a) and no Cyrillic outside the allowlist (Task 8d.6, R41, R43: the Russian column of the spec's glossary, the trigger phrases in the `description` of `SKILL.md`, and the files listed by name — the Russian test fixture and the trigger-eval file `prorab/evals/triggers.json`), both over `prorab/`, `docs/` and the repo `CLAUDE.md`.
- Thresholds (copy into `defaults.json` verbatim): context soft = min(40 % of the window, 500 000 tokens) (R40; it was 60 % until Task 8c.1); context hard = 80 % of the window; 5h day: 60 % no new mass runs, 80 % stop after the current step and wait for the reset; 5h night (night shift only): a window that resets before the morning → stop at 95 % (no separate no-new-mass threshold), the window that covers the morning → 70 % no new mass runs, 80 % stop (≥ 20 % left by the morning), reset time unknown → the day thresholds; morning `night.morning` = `08:00`; week: 50 % notify, 70 % only work orders with a clearance (`clearance_only`); unknown model window = 200 000; Opus 5.5 (`claude-opus-5-5`) window = 1 000 000.
- Budget (R): estimates, spend and the shift budget are counted in US dollars at Anthropic API list prices — a measure of work, not money paid (crews run on the Claude Max subscription). The cost of every assistant message follows the spec's formula from `message.usage`: input × input price, 5-minute cache writes × 1.25 × input price, 1-hour cache writes × 2 × input price, cache reads × cache-read price, output × output price, all per million tokens; usage without a 5m/1h split → the whole `cache_creation_input_tokens` at the 1-hour rate; every `message.id` counts once across all files read. The price table lives in `defaults.json` (`cost.prices`, input / output / cache read in dollars per million tokens: opus 4.00 / 20.00 / 0.20, sonnet 2.00 / 10.00 / 0.20, haiku 0.10 / 0.50 / 0.01, fable 10.00 / 50.00 / 0.25; the family is a substring of `message.model`); a model missing from the table is priced at the highest price in each column. A work order's spend covers every transcript of its crew, attributed by the worktree (all its sessions, their subagents, the `claude -p` runs started in it); the foreman's own research and one-off subagents run under their own dollar estimates; the foreman's own sessions count in the shift's spend on a line of their own. Default shift budget: $100 and +10 pp of the week (stop point A; it was $350). The rate ($ per pp) converts dollars into pp of the 5h window and of the week: estimated from the sensor only; until the first estimate the defaults 3.5 $/pp of the window and 10 $/pp of the week (stop point A; they were 5 $/pp and no week default), always named as defaults, never as estimates; the thresholds themselves are always checked against measured percentages. A work order over its estimate stops after its current step and waits for the customer with a gate, while the others go on; over the shift budget nothing new is issued and every crew stops after its current step, with a gate. Only "ignore limits and finish" lifts these two stops (R42).
- Machine protection — counts, not budget (R): no fixed crew count — the foreman takes the minimum of the ready tasks, the limit bound, the machine-load bound and `parallel_ceiling` = 6; several crews on one site only when their file lists are disjoint; `heavy_slots` = 2 heavy runs machine-wide; 60 heavy runs per stage unless the work order sets its own limit (stop point A; it was 20) (more needs a clearance); default expected duration 30 min. Sessions, subagents, tokens and agent runs are counted per work order for the report only, never as a limit.
- "Ignore limits and finish" (S, R42; the customer's command in any language; kv `override.ignore_limits`) lifts the 5h thresholds (the morning reserve included), the week thresholds, the shift budget and the work orders' estimates until the current goal is done; it never lifts the safety rules (consent prompts, push, PR, release, merge into main) or machine protection (the load bound, heavy slots, the heavy-run limit per stage, `parallel_ceiling`). It is the only exception to the "Never" list below, and only for its estimate-and-budget item.
- Limits from idle sessions are stale (L; Claude Code shows the last API response of THAT session; the countdown keeps running, the percent freezes): per window take the MAXIMUM over all panes / fresh per-session sensor files of the latest `resets_at`; a pane whose countdown shows `(0m)` belongs to the previous window and is ignored for it; an unknown week is `None`, never 0; unknown for > 30 min → `blind_week`; at night an unknown week means no new mass runs.
- Monitor heartbeat 20 min; a crew is "hung" = `working` with no transcript growth for 30 min **and** the newest file of its worktree older than 30 min, never while it holds a heavy slot; when a sign cannot be read the monitor reports it and the foreman never restarts on it (G); at most 2 restarts per work order — a limit screen and a handover never count as restarts (G); a restart counts from a successful `agent start`, whatever the delivery result, and a failure before it changes nothing and never counts (R48, R49).
- G numbers (copy into `defaults.json`, Task 8b.1): at most 6 approval and 10 review iterations per stage, 3 report-fix attempts; a second handover of one work order within 10 min is an incident; the monitor interval grows from 90 s to 300 s while nothing changes and nobody works.
- Never: answer a trust or consent prompt; press "Upgrade" (in "Stop and wait / Upgrade" only "Stop and wait" is ever pressed — G); re-send a prompt's text after `stalled` or `timeout` (G); press Enter on an empty composer (answer 3: Claude Code shows a grey prompt suggestion there, and Enter might submit it); push, open a PR, release, merge into main; exceed an estimate or the shift budget — the one item of this list that the customer's command "ignore limits and finish" lifts while it holds (R42); use `nohup`; delete a worktree with unmerged commits. Every other item holds under that command too.
- Consent prompts (G): six kinds — `trust`, `mcp`, `claude_md_imports`, `bypass_warning`, `api_key`, `tool_permission` — are recognised in the bottom block of the screen only (`screen.tail_lines`; the same holds for limit screens, provider errors and the composer line), named in the gate and the morning report, and never answered; `api_key` means an urgent push to the customer. At most one push per gate or incident (`journal.mark_notified`); everything else goes to the morning report; no reminders.
- Text to a crew (G, answer 2): one line per prompt. Multi-line text (the work order, acts, fix lists) goes into a file under `send.files_dir` = `~/.cache/prorab/work-orders/` — the work order itself is `<id>.md` — and the crew gets one line naming it. Every crew is started with `--add-dir ~/.cache/prorab/work-orders`, so reading the file needs no permission outside the worktree (in bypass mode or not), and nothing is written into the site's worktree.
- Tests must never touch the real `~/.claude` (settings and the `projects/` transcripts), `~/.cache/prorab`, `~/projects/prorab/.beads`, `logs/` or real herdr panes; they use temp dirs, a temp `HOME`, `PRORAB_BEADS_DIR`, `PRORAB_CACHE`, `PRORAB_LOG_DIR` and the fake `herdr` stub. Every test that can reach `crew.message_file`, `send.files_dir` or any other `~/.cache/prorab` path (the work-order files and the `--add-dir` value, slots and their run log, the sensor's `usage/`, `heavy.count`, the events and the crew settings file of Task 14) sets a temp `HOME` and a temp `PRORAB_CACHE` before the defaults load (`_defaults.load` expands `~` from `HOME` at call time), and the tests that write such a file assert that it lies under the temp dir. Never run the status-line tap, `journal.py` or `scheduler.py plan` against real paths: they create real state. Only Task 13 touches real herdr and Claude (and Task 14's first live run, with the customer's consent).

## Review Focus

1. **No limit source at all** (clean install, no sensor, narrow panes): the monitor must report `blind` once, then stay quiet after the foreman acknowledges it (`kv limits.blind_ack`) — not wake the foreman every 90 s forever. Test in Task 7.
2. **A crew `idle` while background shells run** ("N shell" in its status line): not a stop point, no handover. Test in Task 4 (`bg_shells`) and Task 7 (`settled` suppressed).
3. **A crew waiting in a multiple-choice dialog** (`blocked`, but not a consent prompt): the foreman reads the options and answers within the work order; a consent prompt (trust, `.mcp.json`) is never answered. Test in Task 4 (`choice_dialog`) and Task 6 (`answer`). The stale-sensor case stays covered by Task 3's `test_sensor_stale_falls_through`. G: any of the six consent kinds is refused, and a tool-permission prompt is never parsed as a choice dialog (Task 8b.3).
4. **Prompt lost after startup** (`agent_prompt_stalled`): `send` returns `stalled`, never reports success; `timeout` with status `working` afterwards counts as accepted. Test in Task 4. G and answer 3: `send` waits `--until working --until done --until blocked`; after `stalled` exactly one Enter, only at `idle` or `done` (herdr shows `done` after a Claude turn) and only when the visible composer line (the `❯` line between two `─` rules, R45) holds the start of our text — never on an empty composer, where a grey prompt suggestion could be submitted; after that Enter only `working` (accepted) or `blocked` confirm: the wait is `--until working --until blocked`, since a standalone `agent wait` matches the `done` the pane already shows, and anything else or a timeout → `unconfirmed` (R46); the text is never sent twice; `timeout` while not `working` → `unconfirmed`, nothing pressed (Tasks 8b.3, 8b.6).
5. **A second foreman** started while one is alive: refuses (`acquire_active` false); a dead one's lock (pane gone from `herdr agent list`) is taken over. Test in Task 5.
6. **Night reserve**: night shift, 05:30, window at 78 % resetting at 10:00, 4 more tasks ready → no new mass runs (≥ 70), stop at 80, ≥ 20 % left at 08:00; unknown reset time at night → day thresholds. Test in Task 6b (`cap_for`) and Task 7 (`limit` uses `cap_for`).
7. **"Ignore limits and finish"**: no `limit` and no `budget` events while it holds, readings and spend still logged; machine protection still bounds `allowed_parallel`; the work orders' estimates are lifted with the budget, the heavy-run limit per stage is not (R42); it expires when every work order of the goal is accepted or waiting for the customer. Test in Tasks 5, 6b, 7, 8c.6, 8c.7.
8. **Stale limits from idle panes** (L): two panes 17.0 % (idle) and 28.0 % → 28; a `(0m)` pane at 70 % plus a fresh 5 % → 5; narrow panes only → week `None`; context = the first bar of the status line, not the last percent. Test in Task 3 (follow-up commit), Task 7 (`blind_week`), Task 8 (per-session files).
9. **A limit screen is not a failure** (G): no `bump_restarts`; in "Stop and wait / Upgrade" only "Stop and wait" is pressed and `answer` refuses every limit screen; a final provider error goes to the customer at once and replaces `settled` for that crew's episode (R50). Test in Tasks 8b.4, 8b.6, 8b.8.
10. **Consent kinds and pushes** (G): a marker above the bottom block is ignored; `bypass permissions on` in the status line is not a consent prompt; an `api_key` dialog raises one urgent push, and a monitor restart on the same screen raises none. Test in Tasks 8b.3, 8b.5, 8b.8.
11. **The stage report is checked by a script** (G): no commit, an empty branch or any git error → rejection; files outside the work order's "Files" → rejection; at most `cycles.report_fix` fix rounds, then a gate. R: a missing "Heavy runs" line, a reported number that differs from the heavy-run log of `slots.py`, or more heavy runs than the per-stage limit without a clearance → rejection; a count that cannot be verified from records (no `--stage`, or the stage has no start time) → rejection `heavy runs not verifiable`, never the crew's word (R52). Test in Tasks 8b.6, 8c.5.
12. **Monitor economy** (G): with a fresh sensor a steady poll starts exactly two processes (`herdr agent list`, `bd kv list`); `hung` needs both signs; a heavy-slot holder is never hung. R: the spend and the rate are computed by reading files inside the monitor's own process — never a process launch. Test in Tasks 8b.7, 8b.8, 8c.7.
13. **Dollar cost from transcripts** (R): one `message.id` counts once across all files (streamed lines and forked or resumed sessions repeat ids); subagent transcripts and `claude -p` runs in the worktree count; sidechain lines count in the cost while the context still reads only the main chain; an unknown model is priced at the highest price of each column (never cheaper than any known model); usage without a 5m/1h split is priced as 1-hour writes; a sibling directory whose slug shares the worktree's prefix is not attributed. Test in Task 8c.2.
14. **The rate** (R): only sensor readings, both ends of an interval in the same window (the same `resets_at` within 10 min, never across a reset), at least 10 min and 1 pp apart; rate = Σ$ / Σpp over the horizon; until the first estimate the defaults (3.5 $/pp for the window, 10 $/pp for the week; Task 10b.5), named as defaults; a week default set to null in `defaults.json` gives an unknown week rate (`None`), never 0; without the sensor no estimate at all. Test in Tasks 8c.3, 8c.7.
15. **Estimates and the budget in dollars** (R): a work order over its estimate → a `budget` event naming it, that work order stops after its step, the others go on; the shift over its budget → nothing new is issued; a research subagent whose estimate does not fit what is left is refused; the plan converts every estimate into pp by the rate before issuing. Test in Tasks 8c.4, 8c.6, 8c.7.
16. **Language guards** (E, R41): no banned transliteration anywhere in `prorab/`, `docs/` or `CLAUDE.md` (the guard builds its own word list from pieces so it does not trip itself); no Cyrillic outside the `description` of `SKILL.md`, the Russian column of the spec's glossary and the files the test lists by name (the Russian test fixture and the trigger-eval file, R43). Test in Tasks 8a, 8d.6, 12.

#### 10b.4 — a bounded, parallel test runner

**Files:** Create `prorab/tests/run.py`, `prorab/tests/test_run.py`
