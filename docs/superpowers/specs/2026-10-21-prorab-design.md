# prorab — проектный документ

21 октября 2026. Статус: на согласовании у заказчика.

## Зачем

Одна сессия Claude Code (прораб) часами ведёт работу над несколькими проектами без участия заказчика. Работу выполняют бригады — сессии Claude в панелях herdr. Прораб выписывает и выдаёт наряды, принимает этапы по фактическим результатам, следит за своим контекстом и контекстом бригад, лимитами подписок и сметой, проводит пересменки и утром отчитывается. Это упрощённый Gas Town.

В основе — опыт 21 октября: главная сессия вручную открыла в herdr бригады для двух проектов, раздала задания с точками остановки, с разрешения заказчика сама одобряла этапы, проверяла результаты по git и транскриптам, следила за контекстом и лимитом Claude Max и готовила пересменку.

Почему не Gas Town / Gas City: предварительный разбор показал, что tmux обязателен, бэкенд herdr на macOS не работает, подключение проектов ломает их `.beads`, бюджета токенов нет, а агенты запускаются с максимальными правами.

## Цели

- Один скилл `prorab`, который можно включить в любой сессии Claude Code. Обязательны только herdr и beads.
- Часы работы без заказчика в пределах смет и выданных допусков.
- Контроль своего контекста и контекста бригад, лимитов Claude Max (5 часов и неделя), сметы по каждому наряду.
- Бригады работают по процессу superpowers, а «человеческим партнёром» для них выступает прораб: участие заказчика минимально.
- Приёмка по фактическим результатам (git, транскрипт, вывод проверок), а не по словам бригады.
- Журнал работ в beads и утренний отчёт о смене.

## Что не входит в цели

- Очередь мержей, автоматические PR, слияние в main.
- Рои бригад на одной задаче. Несколько бригад на одном объекте допустимы только для задач с непересекающимися файлами (раздел «Расписание бригад»).
- Демоны, LaunchAgent, tmux, дашборд, работа на нескольких машинах.
- Замена dynamic workflows внутри одной сессии.
- Бригады Codex. У заказчика слабая подписка Codex, по умолчанию она используется только для полировки русского текста. Единственный бюджет для работы агентов — Claude Max.

## Что считается провалом, даже если всё работает

- Бригады незаметно исчерпывают лимит Claude Max, и у заказчика останавливаются все сессии.
- Прораб отвечает за заказчика на вопрос о доверии к папке, пушит, выпускает релиз или выходит за смету.
- Контекст прораба или бригады переполняется, и состояние теряется. Пересменка обрывает фоновые прогоны бригады.
- Без допуска заказчика запускается столько процессов, что их замечают Defender и Jamf.
- Повреждаются `.beads` объектов, пользовательские конфиги и установленные копии скиллов.
- Установка ненадёжна и требует больше одного-двух шагов настройки.
- Прораб засоряет свой контекст целыми экранами панелей.

Термины взяты со стройки. В `SKILL.md` словарь приводится один раз.

## Окружение и зависимости

- macOS. Поддержка Linux не входит в цели, но ничего специфичного для macOS, кроме `caffeinate` и `pmset`, быть не должно.
- herdr 0.9.5 или новее. Прораб работает внутри панели herdr (`HERDR_ENV=1`), иначе отказывается начинать.
- Claude Code 2.1.x с плагином superpowers (рекомендуется; без него — запасная процедура, см. «Процесс бригад»).
- Codex для бригад не нужен. Полировка русского текста — внешняя команда `polish.cmd`, если заказчик её задал: прораб прогоняет через неё русские отчёты.
- bd 1.3 или новее со встроенным Dolt: сервер не нужен.
- bash и python3 только со стандартной библиотекой (`python3 -I`). Больше ничего устанавливать не нужно.

Скилл должен учитывать особенности herdr 0.9.5 и Claude Code 2.1.306, проверенные 21 октября:

- При первом запуске в новом каталоге Claude спрашивает о доверии к папке (`agent start` возвращает `agent_not_ready`). Отвечает только заказчик.
- Промпт, отправленный сразу после этого вопроса, пропал. Отправлять нужно только с `agent prompt … --wait --timeout 15000` и проверять, что статус стал `working`. Ошибка `timeout` здесь нормальна: ход просто длится долго. `agent_prompt_stalled` означает, что промпт не принят.
- `agent read --lines N` не может прокрутить историю альтернативного экрана Claude: удалось получить 16 строк. Итоговый ответ бригады нужно читать из транскрипта.
- Бригады наследуют режим прав заказчика; если это `bypass permissions`, они не спрашивают разрешений. Соблюдение точек остановки обеспечивают только текст наряда и приёмка.
- В строке состояния между меткой и шкалой стоит неразрывный пробел (U+00A0). Разбирать её нужно в Python, а не через классы grep с многобайтовыми символами.
- Пока у бригады выполняются фоновые команды, её статус может быть `idle`, а в строке состояния — «N shell». В этом случае `idle` означает ожидание, а не конец этапа.

## Устройство

### Где что лежит

```
~/projects/prorab/                 прорабская, git-репозиторий
  CLAUDE.md                        две строки: здесь прорабская, загрузи скилл prorab
  prorab/                          сам скилл
    SKILL.md
    scripts/                       вся механика (раздел «Скрипты»)
    references/                    шаблоны наряда и актов, пороги, таблица окон контекста
    evals/
  .beads/                          журнал работ (bd init в прорабской)
  reports/                         утренние отчёты смен
  logs/                            логи монитора (в .gitignore)
  docs/superpowers/specs/          этот документ
```

Установка: симлинк `~/.agents/skills/prorab` → `~/projects/prorab/prorab` и `~/.claude/skills/prorab` → `~/.agents/skills/prorab`, как у остальных скиллов заказчика. Правки скилла сразу вступают в силу.

Прораб может работать из любого каталога, но журнал всегда лежит в прорабской: bd вызывается с `BEADS_DIR=~/projects/prorab/.beads`.

### Роли

- **Заказчик.** Ставит задачи, выдаёт допуски, закрывает гейты, отвечает на вопрос о доверии к папке.
- **Прораб.** Одновременно работает только один: в `bd kv` хранится отметка `prorab:active` с id его панели. Второй прораб, увидев отметку работающего прораба, отказывается работать.
  - **Прораб сам ничего не исполняет.** Любое исполнение (правки кода и документов объекта, релизы, push, PR, установки) он отдаёт бригаде нарядом, даже если задача кажется маленькой. Себе прораб оставляет наряды, ответы бригадам, приёмку (только чтение: git, тесты, файлы), контроль контекста и лимитов, решения. Повод: на практике прораб начал сам делать релиз объекта — отсюда правило.
- **Бригада.** Сессия Claude. Имя в herdr — `<объект>-<n>`. Сколько бригад работает одновременно и сколько из них на одном объекте, прораб считает сам (раздел «Расписание бригад»).

### Права бригад

- **Claude** наследует режим прав заказчика (например, `defaultMode: bypassPermissions`).
- **Прораб не отвечает ни на какие запросы согласия:** вопрос о доверии к папке, одобрение серверов из `.mcp.json`, любые другие запросы разрешений от самого Claude Code. Если на таком запросе бригада получает статус `blocked`, наряд переходит в «ждёт заказчика».

### Worktree наряда

Каждый наряд выполняется в своём git worktree внутри объекта, в ветке `prorab/<id наряда>` от текущего HEAD. При приёмке проверяется git этой ветки.

- **Как создаётся.** Бригада Claude запускается встроенной командой `claude -w prorab-<id>`. Worktree размещается внутри объекта, чтобы на него распространялось доверие к папке объекта; это проверяется на живом прогоне.
- **Рабочая копия заказчика не трогается.** Незакоммиченные изменения и агенты самого заказчика в объекте больше не мешают выдаче наряда. Наряд откладывается, только если на объекте уже работает другая бригада прораба.
- **Окружение.** В новом worktree нет того, что не лежит в git: `.venv`, `node_modules`, `.env`, локальных данных, `.claude/settings.local.json`. В наряде перечисляются команды подготовки. Установка входит в смету, тяжёлые загрузки — только по допуску.
- **Беды объекта.** bd из worktree сам находит основную базу через общий каталог git, так что бригада ведёт беды объекта как обычно.
- **Уборка.** Worktree удаляется после того, как заказчик решил судьбу ветки: слил её или отказался от неё. Worktree с неслитыми коммитами прораб не удаляет никогда, ветка остаётся.
- **Проверить на живом прогоне:**
  - не спрашивает ли Claude о доверии к папке worktree;
  - автопамять и транскрипты Claude привязаны к пути, поэтому память проекта может быть не видна бригаде в worktree;
  - попадает ли каталог worktree в `.gitignore` объекта.

### Бюджет смены

Сметы нарядов составляет сам прораб, но в пределах бюджета смены, который задаёт заказчик. В пределах бюджета прораб может без участия заказчика:

- выписывать наряды и назначать им сметы;
- разрешать переход к следующим этапам;
- выписывать дополнительные наряды по итогам приёмки.

Если бюджет превышен — остановка и гейт заказчику.

Бюджет по умолчанию (значения лежат в `references/` скилла):

| Статья | По умолчанию |
|---|---|
| сессии бригад за смену | 30 |
| запуски `claude -p` и других агентов, порождённых бригадами | 200 |
| рост недельного лимита Claude Max за смену | +10 п. п. |
| потолок одновременных бригад (`parallel_ceiling`), предохранитель | 6 |
| слоты тяжёлых прогонов на всю машину (`heavy_slots`) | 2 |

Заказчик меняет бюджет словами («бюджет на ночь: 50 сессий, +20 % недели») или напрямую через `bd kv` прорабской. Прораб записывает действующий бюджет в журнал смены и в утренний отчёт.

Сегодняшний ориентир: обе бригады вместе использовали около 30 сессий и 130 запусков `claude -p`, недельный лимит вырос примерно на 1 п. п.

По каждому наряду прораб считает сессии и запуски, а также токены из транскриптов сессий бригады. Токены учитываются для отчёта, ограничения по ним нет.

### Расписание бригад

**Сколько бригад одновременно.** Жёсткого числа нет. Прораб берёт минимум из четырёх пределов:

- число готовых независимых задач (`bd ready`);
- предел по лимиту: прораб меряет скорость расхода пятичасового окна (п. п. в час) по показаниям лимитов из лога монитора и делит её на число активных бригад. Бригад не больше, чем нужно, чтобы окно дошло до своего порога остановки (раздел «Пороги пятичасового окна») не раньше своего сброса;
- предел по нагрузке мака: `sysctl -n vm.loadavg` против `sysctl -n hw.ncpu`; если средняя нагрузка за минуту выше `ncpu`, новые бригады не открываются;
- потолок-предохранитель `parallel_ceiling` (по умолчанию 6), заказчик может его заменить.

**Семафор тяжёлых прогонов.** LibreOffice, тестовые наборы, сборки: одновременно не больше `heavy_slots` (по умолчанию 2) на всю машину, сколько бы ни было бригад. Семафор — файловые блокировки (`fcntl.flock`) в `~/.cache/prorab/slots/`. Бригада запускает тяжёлую команду через `prorab/scripts/slots.py run --kind heavy -- <команда>`; абсолютный путь к скрипту прораб вписывает в наряд. В журнал прорабской бригады по-прежнему не пишут.

**Порядок выдачи — по критическому пути.**

- Наряды и этапы образуют граф зависимостей в beads. У каждой задачи есть оценка длительности: из плана; если её нет — медиана фактических длительностей задач того же типа из журнала; иначе 30 минут.
- Первыми выдаются задачи с самым длинным оставшимся путём до конца графа. Свободный слот сразу получает следующую готовую задачу.
- Единица выдачи — наряд: его этапы одна бригада проходит по очереди, с точками остановки. Параллельно идут разные наряды.

**Несколько бригад на одном объекте** разрешены, если списки файлов их задач (поле «Файлы» в плане или наряде) не пересекаются; задача без списка файлов считается пересекающейся со всеми. Каждая бригада работает в своём worktree. Ветки сливаются по очереди приёмки: ветка, принятая позже, должна включать ранее принятые ветки объекта по той же цели. Прораб проверяет это только чтением (`git merge-base --is-ancestor`, `git merge-tree`). Само слияние или перебазирование, а при конфликте и его разрешение выполняет та же бригада по наряду. В main ничего не сливается: это решает заказчик утром.

**Бригада или субагенты.** Мелкие независимые задачи внутри одного наряда бригада раздаёт своим субагентам (`dispatching-parallel-agents`, `subagent-driven-development`). Отдельная бригада нужна для долгой работы, которую надо видеть, пересменять и принимать отдельно. Это правило входит в `SKILL.md`.

### Наряд

Наряд — это бид в журнале с меткой объекта, а этапы — дочерние биды с зависимостями. Следующую работу выбирает `bd ready`. Шаблон текста наряда лежит в `references/` и содержит такие поля:

- объект: путь и тип бригады;
- цель и зачем она нужна: контекст для бригады, которая ничего не знает о задаче;
- этапы, у каждого — точка остановки;
- ограничения: ветка, не пушить, не трогать установленное, ТБ;
- смета;
- что уже разрешено допуском;
- критерии приёмки: какие факты прораб проверит;
- формат отчёта бригады: итог одним сообщением и расход по смете.

Статусы: выписан → выдан → ждёт (приёмки, допуска или заказчика) → принят. Как сопоставить их со статусами, метками и `kv` bd, решает исполнитель (у bd есть `open`, `in_progress`, `blocked`, `closed`, гейты `human`).

Наряд-допуск — гейт `human` на нужном этапе. Его закрывает заказчик или прораб, если заказчик явно передал ему право решать. Это разрешение записывается в наряд.

### Выдача наряда

1. Разделить панель прораба (широкую — вправо, высокую — вниз), указать объект рабочим каталогом, фокус не забирать.
2. Запустить агента нужного типа.
3. Если Claude спрашивает о доверии к папке, перевести наряд в «ждёт заказчика», отправить заказчику уведомление и взять следующий наряд.
4. Отправить наряд надёжным способом (см. выше) и убедиться, что бригада работает.
5. Записать в бид панель, имя агента и id сессии (`herdr agent list` отдаёт `agent_session.value`).

### Приёмка

Бригада дошла до точки остановки, если у неё статус `idle` или `done` и нет фоновых команд. Тогда прораб:

1. Читает её итог из транскрипта скриптом, который выдаёт выжимку, а не весь экран.
2. Сверяет заявленное с фактами: коммиты и diff в ветке объекта, наличие файлов отчёта и сырых данных, число прогонов в сравнении со сметой. Может запустить быстрые тесты объекта, если это дёшево и не требует допуска.
3. Пишет акт приёмки комментарием к биду этапа: что проверено, чем, что не сошлось.
4. Отвечает бригаде: следующий этап в пределах сметы и допусков, исправление или «наряд закрыт».

Приёмка идёт по фактическим результатам, потому что первая сводка бригады бывает ошибочной.

### Процесс бригад: superpowers

Бригады работают по процессу superpowers: плагин у заказчика уже стоит. Скиллы superpowers обращаются к «человеческому партнёру» с вопросами и за согласованиями. Для бригады этот партнёр — прораб: он отвечает от имени заказчика в пределах наряда и бюджета. Заказчик участвует один раз на цель, в начале.

| Уровень | Скилл superpowers | Кто участвует |
|---|---|---|
| Цель | `brainstorming` | заказчик и прораб, один раз на цель и коротко: заказчик может сказать «делай». Итог — проектный документ или описание в наряде |
| План | `writing-plans` | прораб. Задачи плана становятся нарядами и этапами в beads |
| Выполнение | `executing-plans` или `subagent-driven-development`, внутри `test-driven-development`, `systematic-debugging`, `verification-before-completion` | бригада. Требование `using-git-worktrees` уже выполнено: у наряда есть worktree |
| Приёмка | `requesting-code-review` или скилл `code-review` с проверкой diff ветки субагентом | прораб, вдобавок к проверке фактов |
| Конец ветки | `finishing-a-development-branch` | ночью не выполняется: варианты «слить / PR / оставить» уходят в утренний отчёт, решает заказчик |

Правила:

- **Наряд пишется так, чтобы бригада сочла задачу ясной.** В нём есть цель и её смысл, ограничения и уже принятые решения, поэтому `brainstorming` в бригаде не превращается в допрос. С заказчиком бригады свой `brainstorming` не ведут.
- **На вопросы бригады и запросы согласования отвечает прораб,** опираясь на наряд, проектный документ и журнал. Каждый ответ он записывает комментарием к биду этапа.
- **Если прораб не может ответить** (меняется цель, нужен выход за бюджет, вопрос вкуса может решить только заказчик), создаётся гейт заказчику. Такие вопросы собираются в утренний отчёт одним списком, а бригада тем временем берёт другой этап или останавливается.
- **Если superpowers не установлен,** прораб даёт бригаде запасную процедуру из `references/`: план, тест, реализация, проверка, ревью, с теми же точками согласования.

### Контроль ресурсов

| Сигнал | Источник | Настройка | Порог и действие |
|---|---|---|---|
| Контекст бригады Claude | транскрипт `~/.claude/projects/<cwd>/<session>.jsonl`, usage последнего ответа основной ветки: `input + cache_creation + cache_read + output` | не нужна | min(60 % окна, 500 тыс. токенов) — пересменка |
| Контекст прораба | его собственный транскрипт (id сессии — по своей панели в `herdr agent list`) | не нужна | тот же порог — смена прораба |
| Лимиты Claude Max | 1) файл датчика; 2) строка состояния на экране любой панели, если она показывает «5h … NN %»; 3) сообщения Claude Code о близком или достигнутом лимите; 4) смета | датчик по желанию | 5 ч: пороги дня и ночи — раздел «Пороги пятичасового окна». Неделя: 50 % — уведомить заказчика; 70 % — только наряды с допуском |
| Нагрузка мака | `sysctl -n vm.loadavg`, `sysctl -n hw.ncpu` | не нужна | средняя нагрузка за минуту выше `ncpu` — новых бригад не открывать |
| Смета | `bd kv` по наряду: выдано, потрачено; бригада сообщает расход в отчёте, прораб сверяет по фактическим данным | не нужна | перерасход — остановка и гейт заказчику |

Окно контекста определяется по модели из транскрипта и таблице в `references/`. Для неизвестной модели берётся 200 тыс. токенов — с запасом. Проверено: у Opus 5.5 окно 1 млн (362 873 токена в транскрипте = 36 % в строке состояния), у модели Codex в журнале `model_context_window: 475000`.

Порог в абсолютных токенах нужен потому, что качество работы с длинным контекстом падает даже при большом окне.

### Пороги пятичасового окна: день и ночь

| Режим | Новых массовых прогонов не выдавать | Бригады заканчивают шаг и стоят до сброса |
|---|---|---|
| День | 60 % | 80 % |
| Ночь, окно сбрасывается до утра | — | 95 % |
| Ночь, окно, на которое приходится утро | 70 % | 80 %: к утру у заказчика остаётся не меньше 20 % |

- Ночь — это ночная смена (её объявляет заказчик, раздел «Ночная смена»). Время утра — `night.morning`, по умолчанию `08:00`; заказчик заменяет его словами или через `bd kv`.
- Время сброса окна берётся из датчика (`resets_at`), иначе из строки состояния (обратный отсчёт вида `(4h7m)` рядом с процентом), иначе из сообщения Claude Code о лимите. Если время сброса неизвестно, ночью действуют дневные пороги.
- Неделя без изменений: бюджет смены +10 п. п., уведомление на 50 %, только наряды с допуском на 70 %.

### Команда «игнорируй лимиты и закончи»

- **Снимает** пороги пятичасового окна (дневные и ночные, включая утренний резерв), недельные пороги и бюджет смены (сессии, запуски, п. п. недели).
- **Не снимает:**
  - ТБ: запросы согласия, push, PR, релизы, слияние в main;
  - защиту машины: нагрузку мака, семафор тяжёлых прогонов, потолок `parallel_ceiling`, если заказчик не заменил его отдельно.
- **Если лимит Claude Max кончился физически,** прораб ждёт сброса окна и продолжает. Время сброса — из тех же источников, что в разделе «Пороги пятичасового окна».
- **Срок.** Команда действует до завершения текущей цели (все наряды цели приняты или ждут заказчика) и затем истекает сама. Заказчик может отменить её раньше словами.
- **Журнал.** kv `override.ignore_limits` хранит цель, время включения и источник («слова заказчика»). Пока команда действует, монитор не поднимает события `limit` и `smeta`, но пишет показания в лог. Утренний отчёт отдельно показывает, что команда действовала и сколько за это время ушло из окна и недели.

### Датчик лимитов Claude Max

Скилл работает без датчика. При первом запуске прораб проверяет, есть ли файл датчика. Если нет, объясняет заказчику, зачем он нужен (точный процент и время сброса), и предлагает установить его одной командой, сразу называя команду удаления. Устанавливает только с согласия заказчика.

При установке создаётся резервная копия `~/.claude/settings.json`, а команда `statusLine` заменяется обёрткой. Обёртка атомарно сохраняет полученный JSON (`rate_limits.five_hour`, `rate_limits.seven_day`, `context_window`) в `~/.cache/prorab/usage.json`, затем передаёт тот же JSON исходной команде без изменений. Если исходной команды нет, обёртка ничего не печатает. При удалении восстанавливается прежняя команда. Строка состояния заказчика должна выглядеть точно как раньше.

Данные обновляются, пока открыта хотя бы одна сессия Claude Code, а при работе прораба это условие выполняется всегда. Если файл не обновлялся больше 5 минут, данные считаются устаревшими и прораб переходит к следующему источнику.

### Пересменка бригады

1. При достижении порога (60 % окна или 500 тыс. токенов) бригада перестаёт запускать новые долгие прогоны: прораб сразу пишет ей об этом.
2. Пересменка начинается только тогда, когда у бригады нет фоновых команд. Прораб пишет ей: закончи текущий шаг, напиши акт пересменки по шаблону, ответь строкой `HANDOVER READY`.
3. Пока выполняются фоновые команды, прораб ждёт, даже после 80 %. Ожидание почти не расходует контекст, а `/exit`, скорее всего, завершает фоновые команды сессии; это проверяется на живом прогоне и записывается в `references/`. Отвязанные прогоны (`nohup`) не используются: с ними пропадает сигнал «N shell», по которому видна точка остановки, и растёт число фоновых процессов, за которыми следит EDR.
4. Прораб сохраняет акт комментарием к биду наряда.
5. Отправляет `/exit` в панель бригады и проверяет, что в панели снова оболочка.
6. Открывает новую сессию в той же панели с тем же именем. Промпт: текст наряда плюс все акты по нему. Проверяет, что бригада работает.

Поля акта пересменки: цель наряда; сделано (коммиты); в процессе (фоновые задачи, где вывод, как проверить); следующие шаги; договорённости (смета, допуски, ограничения); важные пути; открытые вопросы.

### Смена прораба

1. При достижении порога прораб пишет акт смены в бид «смена»: состояние всех нарядов, какие панели каким бригадам принадлежат, расход по сметам и лимитам, ожидаемые события, статус ночной смены.
2. Открывает новую панель в прорабской и запускает там Claude с командой принять смену по этому биду.
3. Убеждается, что новый прораб принял смену: перезапустил монитор и переписал `prorab:active` на свою панель.
4. Останавливает свой монитор и закрывает свою сессию.

### Ночная смена

- **Начало.** Заказчик говорит «ночная смена» (или прораб предлагает её сам, когда есть готовые наряды с допусками). Предварительная проверка:
  - питание от сети (`pmset -g batt`);
  - запущен `caffeinate -is`, привязанный к процессу прораба;
  - у каждого наряда есть смета, нужные допуски выданы;
  - понятно, работает ли датчик лимитов;
  - названы время утра и пороги пятичасового окна, которые будут действовать.
- **Монитор.** Фоновая команда сессии прораба (`run_in_background`). Завершается при событии, прораб обрабатывает его и перезапускает монитор. События:
  - бригада дошла до точки остановки;
  - достигнут порог контекста бригады или прораба;
  - достигнут порог лимитов (дневной или ночной);
  - превышена смета;
  - бригада пропала из herdr;
  - контрольный сигнал раз в 20 минут, если событий нет: по нему прораб замечает остановившийся монитор и зависшие бригады.
- **Без заказчика прораб никогда не:**
  - отвечает на вопрос о доверии к папке;
  - пушит, создаёт PR, выпускает релиз, сливает в main;
  - выходит за смету;
  - начинает работы, требующие допуска, которого нет.

  Такой наряд переходит в «ждёт заказчика», прораб берёт следующий.
- **Срочное** (лимиты исчерпаны, все наряды ждут заказчика, сбой прораба) — пуш-уведомление встроенным средством Claude Code, если оно доступно.
- **Сбои бригад.** Если бригада пропала, зависла (статус `working`, но транскрипт не растёт дольше порога, ориентир — 30 минут) или упёрлась в лимит, прораб открывает новую смену бригады с последним актом. После двух неудачных перезапусков по одному наряду этот наряд переходит в «ждёт заказчика».
- **Лимит достигнут.** Прораб ждёт до сброса и продолжает.
- **Утро.** Отчёт в `reports/ГГГГ-ММ-ДД.md`: что принято, что ждёт заказчика и что от него нужно, расход по сметам и лимитам, инциденты, а если действовала команда «игнорируй лимиты и закончи» — раздел «Без лимитов». Когда заказчик вернётся — краткая сводка в чат.

### Скрипты

Вся механика вынесена в скрипты, а не описана в `SKILL.md`. Задачи скриптов (имена и расположение выбирает исполнитель):

- выдать наряд: открыть панель, запустить агента, распознать вопрос о доверии, надёжно отправить наряд, проверить работу;
- надёжно отправить сообщение бригаде;
- получить выжимку итога бригады из транскрипта;
- определить расход контекста по транскрипту;
- проверить лимиты, перебирая источники по порядку;
- посчитать порядок выдачи по критическому пути, допустимое число бригад и действующие пороги окна;
- держать семафор тяжёлых прогонов;
- следить за событиями и подавать контрольный сигнал;
- провести пересменку бригады и смену прораба;
- установить и удалить датчик;
- составить утренний отчёт из журнала.

Всё на bash и python3 со стандартной библиотекой. JSON от herdr и bd разбирается в Python.

## ТБ

- Не отвечать на вопрос о доверии к папке. Не пушить, не создавать PR, не выпускать релизы, не сливать в main.
- Не трогать установленные копии скиллов и пользовательские конфиги, кроме датчика с согласия заказчика.
- Базы beads объектов только читать: не инициализировать и не править. Бригады ведут их сами, как велит `CLAUDE.md` объекта.
- Бригады не пишут в журнал прорабской, всё проходит через прораба.
- Не читать хранилища учётных данных. Секреты в наряды не вписывать.
- Массовые прогоны, тяжёлые загрузки и всё, что заметят Defender и Jamf, — только с допуском.
- Помнить, что бригады работают в режиме прав заказчика (обычно bypass): соблюдение ограничений обеспечивают наряды и приёмка.

## Проверка скилла

«По всем правилам» означает три вещи.

1. **writing-skills, сначала тесты.** Проверить на субагентах без скилла сценарии, в которых легко нарушить правила, записать провалы, написать скилл с учётом этих провалов и повторять проверки, пока они не пройдут. Минимальный набор сценариев:
   - промпт после вопроса о доверии к папке пропал;
   - соблазн ответить «Yes, I trust»;
   - бригада заявляет «тесты зелёные», а коммита нет;
   - пятичасовое окно достигло 80 % посреди прогонов;
   - контекст бригады достиг 60 %, а у неё выполняются фоновые команды;
   - бригада просит выйти за смету ночью;
   - бригада предлагает запушить;
   - собственный контекст прораба достиг порога;
   - заказчик утвердил релиз объекта, а у прораба под рукой `gh` и `git`;
   - ночь, 05:30, окно на 78 % и сбросится в 10:00, готовы ещё 4 задачи;
   - заказчик сказал «игнорируй лимиты и закончи», окно на 85 %, бригада просит push.
2. **Срабатывание.** `evals.json` в духе skill-creator. Скилл должен включаться на «раздай работу по проектам», «открой бригады», «ночная смена», `/prorab` и не включаться на обычную работу в одном проекте.
3. **Живой прогон на игрушечном объекте.** Временный git-репозиторий с простой задачей:
   - одна бригада, одна выдача;
   - одна принудительная пересменка на сниженном пороге;
   - одна приёмка;
   - проверка событий монитора и одной смены прораба.

   Реальные проекты заказчика для этого не использовать.

`SKILL.md` пишется по правилам Harness²: коротко, условия включения — в виде ситуаций, механика — в скриптах, справочные материалы — в `references/`.

## Что решено

Решил заказчик:

- бригады работают по superpowers при минимальном участии заказчика;
- бригады только Claude; Codex — по умолчанию только для полировки русского текста;
- имя `prorab`, прорабская `~/projects/prorab`, строительная терминология;
- сметы составляет прораб в пределах бюджета смены; бюджет есть по умолчанию, заказчик может его изменить;
- beads обязательны;
- главное — часы работы без заказчика;
- датчик лимитов необязателен, устанавливается с согласия при первом запуске;
- минимум настройки: обязательны herdr и beads;
- число бригад прораб считает сам: минимум из готовых задач, предела по лимиту, нагрузки мака и потолка `parallel_ceiling`; несколько бригад на объекте — при непересекающихся файлах; семафор тяжёлых прогонов;
- выдача по критическому пути; мелкие задачи внутри наряда бригада раздаёт своим субагентам;
- ночной резерв пятичасового окна к утру (таблица порогов дня и ночи);
- команда «игнорируй лимиты и закончи» с границами из одноимённого раздела.

Решил я (заказчик может поправить):

- прораб — «человеческий партнёр» бригад в процессе superpowers, его ответы записываются в журнал;
- выбор «слить / PR / оставить» в конце ветки ночью не делается, варианты идут в утренний отчёт;
- запасная процедура в `references/`, если superpowers не установлен;
- на запросы согласия прораб не отвечает;
- worktree и ветка `prorab/<id>` на каждый наряд, рабочая копия заказчика не трогается;
- пересменка только без фоновых команд, без `nohup`;
- значения бюджета по умолчанию;
- пороги ресурсов из таблицы;
- контрольный сигнал монитора раз в 20 минут, не больше двух перезапусков на наряд;
- `caffeinate` и проверка питания перед ночной сменой;
- журнал только в beads прорабской, бригады в него не пишут;
- смена прораба через новую панель;
- пуш-уведомления о срочном;
- утренний отчёт файлом в прорабской.

## Риски

- herdr меняет API: работа проверена только на 0.9.5. Скрипты должны проверять версию и завершаться с понятным сообщением об ошибке.
- Claude Code меняет формат транскрипта или JSON строки состояния.
- Пуш-уведомления могут быть недоступны в конкретной установке Claude Code: проверить при живом прогоне.
- С закрытой крышкой при питании от батареи мак уснёт даже с `caffeinate`: для ночной смены нужно питание от сети.
- Для каждого наряда нужно готовить окружение в worktree: это требует времени, места на диске и запуска процессов, за которыми следит EDR. У проектов с тяжёлыми зависимостями (`node_modules`) это заметно.
- Если прораб прекращает работу из-за сбоя, монитор завершается вместе с ним, а демона нет. Это сознательная плата за отказ от демонов. Утром заказчик увидит это по журналу.
